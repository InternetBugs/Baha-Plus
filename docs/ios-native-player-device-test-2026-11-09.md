## IOS-DEVICE-01：AirPods 单耳取下未自动暂停

**反馈已记录，摘耳事件的具体投递路径尚未捕获。**

源码中已有 `AVAudioSession` 中断开始、`oldDeviceUnavailable` 及系统远程暂停处理，不能归因为完全缺少耳机或系统控制支持。相关位置：

- `app/ios/Runner/AppDelegate.m:23` 注册音频通知，`:113` 注册系统播放控制，`:158`、`:165`、`:172` 转发中断及路由失效的暂停。
- `app/lib/data/playback_environment.dart:32` 检查前台、当前文档及可控制状态。
- `app/lib/ui/official_browser.dart:289` 将接受的系统控制路由到原生播放器。
- `app/lib/data/native_playback.dart:266` 执行原生暂停。

确定存在的交接缺口是：`app/assets/adapters/player.js:537` 注册了网页 Media Session 回调，但 `:381` 的网页命令入口在原生接管时返回 `false`；`:526` 的接管操作没有释放这些回调，只有 `:500` 的整体 dispose 才清理。**如果摘耳的系统暂停仍投递给网页，这条路径不能暂停 AVPlayer。** 本轮没有事件链日志，尚不能证明摘耳实际走了该路径。

另有诊断缺口：`AppDelegate.m:144` 在异步转发后立即向系统返回成功，未记录 Flutter 是否接受以及最终是否暂停。单耳取下和整个音频路由断开也需要分别验证。

建议先处理接管时的网页媒体控制权交接，并补充系统命令来源、音频通知类型、Flutter 拒绝原因及最终暂停结果的诊断。复验应分别覆盖左右单耳、双耳、按柄暂停、控制中心暂停和真正断开蓝牙。

## IOS-DEVICE-02：播放界面发热

**维护者的体感现象成立，热源尚未确定。** USB 充电是干扰因素，不能据此排除播放界面的负载问题，也不能直接认定是发热原因。

本轮性能记录：

- Flutter 弹幕层诊断共 69 个窗口，帧率中位数约 **119.96 FPS**，最低窗口约 **109.01 FPS**。这是 ticker 活跃时收到的 Flutter 帧统计，不是视频源帧率，也不是弹幕单独耗时。
- 按最近一次播放健康采样近似归类，原生正片播放中的 Runner CPU 中位数约 **19.41%**、P95 **59.75%**，以单个逻辑核心为 100%；不能解释为整机 CPU 比例。
- 全段 Runner physical footprint 约 **273—919 MiB**；末次约 **441 MiB**。未包含独立 WebKit 辅助进程，不能据此认定内存泄漏或归因发热。
- 有 8 个 raster 帧超过 16.667ms，最大约 38.928ms。当前诊断使用 16.667ms 阈值，不能充分评价 120 FPS 下约 8.33ms 的帧预算。

源码负载候选：

- `app/lib/ui/native_video_surface.dart:98` 每次 ticker 更新绘制位置；`:136` 只检查播放、缓冲及弹幕开关，没有独立 60 FPS 上限，也不因当前没有可见弹幕而停止连续刷新。
- `app/lib/data/native_playback.dart:231` 每 250ms 查询位置；依赖播放器也有自身位置查询。状态通知会经 `app/lib/ui/official_browser.dart:857` 发起 WebView 原生时钟同步，属于额外负载候选。
- 文字及位图缓存有 64 个 painter、16 MiB 位图预算，当前证据不支持“缓存无界增长”的结论。

建议在相同画质、亮度、片段和初始温度下，对比充电与不充电、弹幕开关，以及弹幕绘制限至 60 FPS 前后的结果；同时新增温控状态及其变化事件。仅降低弹幕绘制频率不代表整个视频管线也降至 60 FPS。

## IOS-DEVICE-03：暂停时弹幕偶发错位

**发现可解释现象的代码触发链，尚未与本轮具体画面对上。**

`NativePlayback` 每 250ms 更新一次自身位置。暂停命令调用播放器后，依赖可能先同步发布“已暂停”，宿主随后才重新查询准确位置，因此界面可能短暂收到“已暂停＋旧位置”。

`app/lib/core/danmaku_animation.dart:39` 在 `running=false` 时直接将呈现时钟重设为传入位置，绕过播放中的平滑纠偏。`:72` 的轨道管理器在时间回退超过 250ms 时清空轨道分配。因此，小幅位置回退可能同时造成横向回跳和重新分轨后的纵向变化。

相关位置：

- `app/lib/data/native_playback.dart:231`、`:285`、`:312`：位置采样和暂停顺序。
- `app/lib/ui/native_video_surface.dart:126`：将状态交给弹幕时钟。
- `app/lib/core/danmaku_animation.dart:39`、`:72`：时钟重设与轨道清空条件。

建议区分普通播放转暂停与显式 seek：普通暂停冻结当前呈现时钟，随后校准最终位置时保持现有轨道；显式拖动仍应允许重建。单纯放宽 250ms 阈值不能解决横向回跳。

现有 `app/test/danmaku_animation_test.dart:44` 的暂停用例恰好使用与插值一致的位置，未覆盖旧采样暂停。应补充旧位置暂停、准确位置补到、恢复播放、暂停中 seek 及原轨道保持用例，再做实机对照。

## IOS-DEVICE-04：长时间息屏后 App 自动刷新并放弃原有缓存

**维护者于同日补充明确：App 内放弃了原有缓存，并自动刷新视频播放。** 本项归入息屏后的播放会话及已缓冲媒体恢复问题。“原有缓存被放弃”是维护者对现象的描述，尚未通过媒体请求或 buffered ranges 的前后对照确认具体清理机制。仍缺少息屏持续时间和准确唤醒时间。

需要核对的源码路径：

- `app/lib/ui/official_browser.dart:76` 在 hidden／paused 时暂停，resumed 时恢复前台标记；`app/lib/data/native_playback.dart:323` 不会在回前台时主动播放，保持暂停符合当前设计。
- `app/lib/ui/official_browser.dart:909` 的授权时钟同步若在前台超时、返回错误或文档不匹配，会调用 `NativePlayback.block()`。
- `app/lib/data/native_playback.dart:328` 设置 `_blocked=true`，没有同控制器内的 unblock 路径；这条路径显示重试，单独不足以解释维护者描述的自动刷新。
- `app/lib/data/app_store.dart:1015` 的 WebContent 退出恢复在正片、前台、原先播放中且未超出次数限制时调用 `reloadBrowser()`；`:977` 会重新加载官方页面并尝试恢复时间线。若唤醒时才收到退出事件，这是一条应对时验证的自动重载路径。
- 网页回退后，`app/assets/adapters/player.js:307` 起的 `tick()` 会针对持续约 20 秒的播放停滞或特定媒体错误调用 `recover()`；`:151` 的恢复函数会解除旧缓存切源并调用 `nativeQuality.reload()`。`app/assets/adapters/native-hls.js:91` 的重载最终重新设置媒体源，可能放弃当前媒体实例的已有缓冲。原生接管仍活跃时，网页 `tick()` 提前返回，不能把网页恢复路径直接套到原生播放上。

这些是与自动刷新有关的候选路径，**尚不能认定本次长时间息屏触发了其中哪一条。** 本轮已有原生初始化失败后进入网页 `native-hls` 后端的证据，必须先确定出问题时的实际后端。原生路径本身不启用旧 WKWebView `PlaybackCache` 回环切源，不能仅凭“缓存”一词认定是该模块清理。

本轮性能窗口中 Runner PID 始终为 `26641`，未出现超过 10 秒的性能采样间隔；应用健康日志有约 240 秒、109 秒、167 秒的间断，但诊断采样本来就会在后台停止，间断也可能与页面状态有关。没有记录到明确的 `web-content-process-terminated` 标记。以上不足以确认具体重载原因。

建议增加前后台事件、当前后端、播放器实例创建／释放、重载来源与原因、前后缓冲区间的脱敏诊断。复验时分别进行短息屏、数分钟息屏、较长息屏及期间网络变化，观察是否触发媒体源或整个页面重载。仍有效的会话应优先沿用，保留缓冲、位置和暂停意图；确实失效的会话再按官方流程恢复。

## IOS-DEVICE-05：收藏成功后跳 Web 再返回根页面

**详情收藏会退出原路由及显示 WebView 的代码路径已确认。**

调用链：

1. `app/lib/ui/detail_page.dart:140` 先 `popUntil(route.isFirst)`，再调用 `toggleFavorite`，原详情及其下方的非根路由已经退出。
2. `app/lib/data/app_store.dart:897` 用 `BrowserIntent.favorite` 加载官方页面，明确 `visible: true`。
3. `app/lib/ui/official_browser.dart:691` 页面完成后交给 `navigationFinished`，后者执行 `retryFavorite` 并注入收藏操作脚本。
4. 官方控件确认收藏状态后发送 `favorite-complete`，`app/lib/data/app_store.dart:1332` 开始账号同步。
5. `app/lib/data/app_store.dart:1206`、`:1298` 收到账户消息后隐藏 WebView，却不恢复先前退出的页面层级。

这能解释“详情消失 → WebView 出现 → 根页面出现”。**收藏链中没有发现把 `store.tab` 强制设成首页的逻辑。** 如果入口确实为“片库／我的追番”，最终为何选中首页标签仍需路由与 tab 事件来确认，不能把这一段也视作已完全定位。

另有次要候选：`app/assets/adapters/favorite-action.js:12` 使用 `button.click()`，若官网祖先链接的默认行为未被拦截，可能产生额外网页导航。本轮没有相应 URL 轨迹，不认定其已发生。

建议保留详情路由和来源上下文，让已登录的正常收藏通过现有官方会话静默执行；需要登录或验证时，再显示可返回的官方界面。移除 `popUntil` 必须同时处理认证界面的呈现，避免根层 WebView 被详情覆盖。播放器也调用 `toggleFavorite`，应分别验证入口，保留现有请求 ID、来源、番剧 ID 和目标状态校验。

验证应覆盖收藏和取消收藏、已登录和未登录、同步失败及迟到消息，断言详情、来源 tab、筛选和滚动位置保持。现有测试覆盖收藏状态与消息校验，未覆盖这条完整导航行为。

## 后续实现：禁止原生失败静默回退 WebView 正片

此项针对用户后来指出的独立缺口，不能把旧包的两次 `StateError` 直接当作修复后失败行为的证据。当前代码已包含：

- 启用原生后端时，`player.js` 的 `requiresNative` 与 `native-playback.js` 的 `hold` 在准备接管期间暂停 HTML 正片，并保留接管前播放意图；正片的网页播放、定位和画质命令被拒绝，网页正片恢复／切源路径不再用于接管失败后的自动续播。
- `OfficialBrowser._prepareNativePlayback` 在媒体源准备、初始化／交接失败后发布错误状态，显示错误与显式重试入口，并调用 `failNative`；返回空媒体源也走此路径，避免被暂停的网页正片反复准备却没有重试入口。`PlayerPage` 的加载占位层不再覆盖错误按钮；宿主回归使用真实点击验证重试。`playerCommand` 对原生准备中、已经尝试或已经接管的正片拒绝退回网页命令。显式重试可以重新加载官方流程，代码不把失败静默转成 `native-hls` 正片。
- 成功接管后停止网页播放器轮询，释放网页 Media Session，并卸载 HTML 媒体播放管线；正片画面、实际时间线和控制由原生播放器处理。播放健康采样在原生活动时直接读取原生状态。
- `NativePlayback._load` 新增失败阶段、耗时和受限错误代码，宿主补充初始化／交接失败诊断；不记录签名媒体 URL、Cookie 或账号令牌。这些新增信息不能追溯还原旧日志中两次统一 `StateError` 的底层原因。

**官方广告、年龄确认及账号／授权界面仍保留在 WebView。** 官方授权状态检查、观看进度回写、剧集上下文及弹幕数据仍需会话桥接；播放器收藏也使用官方会话。因此，此处的目标是隔离原生正片播放管线和禁止静默降级，不能写成“WebView 或桥接已完全移除”。上述限制适用于启用原生后端的模式；显式关闭 `BAHA_IOS_NATIVE` 的对照包仍属于网页播放路径。
